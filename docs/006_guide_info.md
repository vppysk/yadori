# 案内情報（館内の情報と外部の情報源の統合）

2026-09-27 決定・実装。`docs/002_facility_master_design.md`（資料と承認）と、外部の情報源（旧 `/admin/sources`、`external-sources.ts`）を1つにまとめた。マイグレーションは `20261004000000_guide_info_sources.sql`、URLの取得は `src/server/source-fetch.ts`、読み取りと承認は `src/server/info-sources.ts`。

## 0. 方針と決定事項

- **メニューは「案内情報」1つ**。旧「館内の情報」と「外部の情報源」は、どちらもAIの案内の出どころなので分けない。左の一覧は「未回答の質問 → 資料 → 全体 → 各施設」
- **資料の種類は ファイル（PDF・画像・テキスト）／文章／URL**。URLも資料の1つとして扱う
- **反映のしかたはURLごとに選ぶ**（2026-09-27 追加。6章）。「承認して反映」は、登録時に取得して読み取り、確認・承認する。定期取得で内容が変わったら読み直し、「更新の確認待ち」にして承認を経てから差し替える（承認までは前の版で案内）。「自動反映」は運行情報・天気など刻々と変わる情報向けで、承認を待たずに要約を案内に使う。ファイル・文章は承認して反映だけ
- **外部情報のフラグ**: 管理主体がホテルの外にある資料（公式サイト、自治体・交通機関のお知らせのPDFなど）に付ける。種類に関係なく付けられる。資料の一覧・確認画面・施設の内容の出どころに「外部」と表示し、AIには出どころを添えて案内させる
- **権限は資料全般で1つ**（`knowledge.facility.edit`）。旧「外部の情報源を登録」（`knowledge.source.edit`）は廃止し、持っていたグループ・メンバーには `knowledge.facility.edit` を付ける

### 旧「外部の情報源」から変わること

| | 旧 外部の情報源 | 案内情報のURL資料 |
|---|---|---|
| 反映 | 取得のたびにAIが要約し、確認なしで【外部の最新情報】としてゲストに案内 | 読み取った施設・項目・期間の値を、承認してから案内に使う |
| 更新 | 自動で差し替わる | 「更新の確認待ち」→ 承認で差し替え。承認までは前の版 |
| スタッフへの通知 | 影響が大きいとき（運休・警報など）に現場スマホへ | 更新を検知したら、資料を承認できる人へ「更新を確認してください」 |
| AIへの渡し方 | 【外部の最新情報】（取得時刻付き） | 【最新の館内情報】の中で、値に「（外部情報: 資料名）」を付ける |

上の表は「承認して反映」の場合。運行情報・天気のように刻々と変わる情報は、承認を待つと案内に間に合わないため「自動反映」を選ぶ（6章）。取得間隔と、期間を限定して頻度を上げる仕組み（台風の接近など）はどちらにもある。

## 1. データ

`info_sources` に列を足し、旧 `external_sources` の行を移す（IDはそのまま）。

- `url`（URL資料のとき）、`is_external`（外部情報）、`purpose`（URLで見る内容。読み取りのヒント）
- 取得: `fetch_interval_minutes`・`active`・`last_fetched_at`・`last_success_at`・`last_status`・`last_error`
- 版: `content_hash`（今の本文 `body` のハッシュ）、`pending_body`・`pending_hash`（更新の確認待ちの本文）、`dismissed_hash`（「この更新を見送る」にした版。同じ内容を再び確認待ちにしない）
- 状態 `status`: `pending`（確認待ち）／`approved`（承認済み）／`update_pending`（承認済み・更新の確認待ち。前の版の値で案内中）
- `external_source_boosts` は `info_source_boosts` にして `info_sources` を指す。`external_snapshots` と `external_sources` は削除する
- 旧 外部の情報源は `pending`・本文なしで移す。次の定期取得で読み取られ、確認待ちになる（クラウドの環境には登録がなく、移した行はなかった）

## 2. 処理

- **URLの登録**（`createUrlSource`）: Tavily Extract で本文を取得 → 読み取り（ファイル・文章と同じ `extract`）→ 確認待ち。取得できなければ登録しない
- **定期取得**（`/api/cron/sources`、1分ごと）: 取得間隔を過ぎた有効なURL資料を取得する。AIエージェントの権限 `integration.web_fetch.read` と項目ルール（Webページの内容の読み取り）を確認する
  - 本文のハッシュが今の版・確認待ちの版・見送った版のどれとも違えば、読み直す
  - 確認待ち（`pending`）なら本文と読み取り結果を差し替える
  - 承認済みなら `update_pending` にして、新しい本文と読み取り結果を持つ。資料を承認できる人に通知する
- **承認**（`approveSource`）: 確認待ちの版があれば本文をそれに差し替え、値を置き換える
- **更新を見送る**: 確認待ちの版を捨てて承認済みに戻す（`dismissed_hash` に残す）
- **読み取り**: 外部情報の資料は、館内の施設だけでなく周辺の施設・交通機関なども施設として挙げさせる（`extract` の `external`）。館内向けの指示のままだと、「きたひろしま総合運動公園の芝生広場 9:00〜17:00」を「全体」の営業時間として読み、AIが結びつけられなかった（2026-09-27 検証）
- **AIへの渡し方**: 外部情報の資料から読み取った値に「（外部情報: 資料名）」を付ける。外部の値があるときは、Web取得の連携の指示（`/manage/integrations` で編集）を回答の指示に足す。Nemotronは指示しても「（外部情報：○○）」をそのまま回答に写すため、`cleanReply`（`answer-context.ts`）で「（○○の情報）」に置き換える
- 旧【外部の最新情報】（`getExternalUpdates`）と回答係の `used_sources` は削除する

## 3. 画面

- サイドバー: 「案内情報」（`/admin/knowledge`）。「外部の情報源」は削除し、`/admin/sources` は資料へ移す
- 資料の追加: ファイル／文章／URL。「外部情報（ホテル以外が管理している）」のチェック。URLのときは見る内容と取得間隔
- 資料の一覧: 状態（確認待ち／更新の確認待ち／承認済み）、「外部」「Web」のラベル、URLの最終取得と失敗
- 資料の確認画面: URL資料なら取得の設定（取得間隔・取得を止める・今すぐ取得・期間を限定して頻度を上げる）。更新の確認待ちなら「Webページが更新されました。承認するまで前の内容で案内します」と「この更新を見送る」
- 施設の画面: 値の出どころの資料名に「外部」を付ける

## 4. 確認したこと（2026-09-27）

- URL（JR北海道の運行情報JSON）を画面から登録 → 取得・読み取り → 確認待ち → 承認。遅れがない日は「現在、遅れに関する情報はありません」だけで、案内に使う内容は0件になった（「通常どおり」の記述は読み取らない既存の規則どおり）
- 承認済みのURL資料で本文が変わったことにして取得 → 「更新の確認待ち」になり、資料を承認できる人（田中）に通知。「この更新を見送る」で承認済みに戻る
- 外部情報の文章資料（周辺の運動公園）を承認 → ゲストの質問に「（北広島市観光案内の情報）」を添えて回答

## 5. 未決・残タスク

- 自動反映の要約は資料名で出典を示すが、回答係が `used_sources` を返さないことがあるため、回答文に資料名（括弧書きを除く）が出ていれば出典とみなしている

## 6. 自動反映（2026-09-27 追加）

運行情報・天気など刻々と変わる情報は、承認を待つとゲストの案内に間に合わない。URLの資料ごとに「承認して反映」か「自動反映」を選べるようにした（権限は分けない。`knowledge.facility.edit`）。

- **中身の持ち方**: 自動反映は施設・項目・期間の値に読み取らない。取得のたびに中型が要約し、ホテルへの影響（影響なし／お知らせ／要注意）とスタッフへの配信文を判断する（旧 外部の情報源と同じ方式、`source-fetch.ts` の `analyze`）。値に読み取って自動で承認すると、施設の新規作成や期間の重なりの判断を誰も確認しないことになるため
- **回答への渡し方**: 【自動取得の最新情報】として、資料名・取得時点・要注意・外部情報の印を付けて渡す（`getAutoUpdates`）。最後に取得できてから取得間隔の3倍と3時間の長い方を過ぎた要約は使わない。回答係は使った資料名を `used_sources` で返し、ゲスト画面に出典のリンクを出す
- **通知**
  - 現場スマホ（既存の通知画面、種類 `external_update`）: 要注意は内容が変わるたび、お知らせは影響なしから上がったとき、影響がなくなったときは「影響は解消しました」として通知する（天気予報の細かな更新で通知が続かないように）。宛先は引き継ぎに対応できる人とAI相談を使う人
  - 管理PC: 内容が変わった資料に未確認の印（`unseen_update`）を付け、サイドバーの「案内情報」、左の一覧の「資料」、資料の一覧の行にバッジを出す。誰かが資料を開くと消える（資料を扱える人にだけ出す）
- **切り替え**: 資料の確認画面の「反映のしかた」で切り替える。自動反映にすると、承認して案内に使っていた値はこの資料から外れる。承認して反映に戻すと要約は使わなくなり、読み取り直して確認待ちになる。どちらも切り替えたらすぐ取り直す
- **画面**: 自動反映の資料を開くと、承認の表の代わりに最新の要約・影響・スタッフへの配信文・内容が変わった日時と、取得の設定を出す
- 確認したこと: JR北海道の運行情報を自動反映に切り替え → 要約されてバッジが付き、開くと消えた。前回を要注意にして取り直すと、現場スマホの7人に「影響は解消しました」が届いた。ゲストの「千歳線は今日遅れていますか？」に「現在、遅れ・運休の情報はありません（JR北海道 運行情報 9/27 20:39時点）」と答えた
