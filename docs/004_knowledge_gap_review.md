# 会話ログの定期評価と追記の提案（未回答の質問の作り直し）

2026-09-27 決定。未実装。`docs/003_unanswered_and_handoffs.md` の「未回答の質問」を置き換える。

## 0. 方針と決定事項

- **未回答の質問は、会話ログを定期的に評価して見つける**。ゲストの1通ごとにその場で記録する方式（回答係が返す `unanswered_questions` と正規表現）はやめる
- 目の前のゲストへの応対は対応アラート（引き継ぎ）が受け持つ。未回答の質問は、AIが答えられなかった穴を埋めて**次から答えられるようにする**ためのもの。一覧に出るまでに定期実行の間隔の分だけ遅れるが、困らない
- 評価で「AIが答えられなかった」と判定できた質問を、**追記の提案**として管理PCに出す。スタッフの接点は今と同じく「未回答の質問に答える」だけで、RAGとマスタのどちらに入れるかはスタッフに判断させない（`docs/002_facility_master_design.md` 0章）
- **期間のある回答は資料として登録する**。「年末年始の営業時間」のように期間で変わる内容を「よくある質問」（RAG）に入れると、期間の違う情報が混ざったときに滞在日に合わない案内をしうる（`docs/002_facility_master_design.md` 0章の実験）。登録時にサーバーが判定し、期間のある内容は資料（文章）として既存の読み取り → 承認の流れに乗せる。登録先はスタッフに選ばせない（6章）
- **デモでは「今すぐ評価する」ボタンを置かない**。すでに定期実行されたものとして、提案と評価の記録をデモデータで再現する（5章）

### リアルタイム記録をやめる理由

リアルタイム記録には、次の抜けがあった（`docs/003_unanswered_and_handoffs.md` 10章）。

| 場面 | リアルタイム記録 | 定期評価 |
|---|---|---|
| AIが「スタッフに確認します」と答えた | 入る（回答係の判断と正規表現に頼る） | 拾える |
| 回答を作れなかった（システムの不具合） | 入らない | 拾える |
| 「コインランドリーある？スタッフと話したい」（AIが答える前に引き継ぎ） | 入らない | 拾える |
| スタッフと話している間の質問 | 入らない | 拾える |
| AIが間違った・不十分な答えを返し、ゲストが聞き直した・不満を示した | 入らない（AIは答えたつもり） | 拾える |
| 同じ意味で言い方の違う質問 | 別々の行になる（文面の完全一致でしかまとまらない） | 意味でまとめられる |

加えて、スタッフが代わりに答えていれば、その返信を回答の下書きにできる。

## 1. 処理の流れ

1. **定期実行**: `/api/cron/knowledge-review` を1日1回（深夜）呼ぶ。外部の情報源（`/api/cron/sources`）と同じく `CRON_SECRET` で保護し、開発時は `npm run dev:cron` から呼ぶ
2. **対象の会話**: 前回の実行以降にゲストの発言があった会話（`channel = 'guest'`）。ゲストの発言がない会話や、オーダーの受付だけの会話（実績の業務の種類がオーダーだけ）は評価しない
3. **評価**: 会話ごとに中型（Super）で、ゲストの質問ごとに「AIが答えられたか」を判定する（強制ツール呼び出し、`generateStructured`）。渡すのは会話の全文（ゲスト・AI・スタッフ）と、評価の日付
   - 判定の理由（`reason`）: AIが「確認します」と答えた／情報にない推測で答えた／ゲストが聞き直した・不満を示した／スタッフが代わりに答えた／AIが答える前に引き継いだ／回答を作れなかった
   - 抜き出すもの: 質問（部屋番号・氏名などの個人情報を除いた一般的な形に言い換える）、根拠のメッセージ、スタッフの答え（あれば）
   - 答えられた質問、ゲスト個人の予約内容の質問（「私の予約は何泊？」など、知識に入れるものではない）、オーダーは提案にしない
4. **まとめる**: 質問を埋め込み（Qwen3-Embedding-8B）、未処理の提案と似ていれば（コサイン類似度がしきい値以上）同じ提案に根拠を足して回数を増やす。似たものがなければ新しい提案にする
5. **下書き**: スタッフの答えがある提案は、中型でそれを回答の下書きにする（個人情報とその場限りの内容を除く）。ない提案は下書きなし
6. **記録**: 実行ごとに、評価した会話の数・見つけた質問の数・新しい提案の数・費用を残す（画面の「最終評価」に使う）

LLMの呼び出しは `recordLlmCall`（用途 `knowledge_review`）で計測し、ダッシュボードの費用に含める。

## 2. データ構造（案）

`unanswered_questions` を置き換える。

- `knowledge_gaps`（追記の提案）: `id`・`hotel_id`・`question`（代表の質問文）・`embedding`・`ask_count`・`first_asked_at`・`last_asked_at`・`draft_answer`・`status`（`open`／`answered`／`dismissed`）・`answer`・`answered_by`・`answered_at`・`document_id`（よくある質問として登録したとき）・`source_id`（資料として登録したとき）
- `knowledge_gap_evidences`（根拠）: `gap_id`・`conversation_id`・`message_id`（ゲストの質問）・`reason`・`question`（その会話での言い方）・`staff_answer`・`review_run_id`
- `knowledge_review_runs`（評価の記録）: `id`・`hotel_id`・`started_at`・`finished_at`・`cursor`（今回評価した最後の発言の時刻。次回はこれより後を見る）・`conversations`・`questions`・`new_gaps`・`cost_usd`・`status`・`error`

既存の `unanswered_questions` の未処理の行は、根拠なしの提案として移し、テーブルを削除する。

## 3. 画面（管理PC）

ホームの「未回答の質問」を置き換える（サイドバーの項目名も「未回答の質問」のまま）。

- 見出しの横に「最終評価 9/27 03:00（会話 42件）」を出す
- 各提案: 質問、聞かれた回数、最後に聞かれた日時、判定の理由のラベル（「スタッフが回答」「聞き直し」など）
- 提案を開くと、根拠の会話の一覧を出し、選ぶと対応アラートと同じ会話パネルで該当のメッセージを開く（読むだけ。返信はしない）
- 回答欄は下書きがあれば入れておく。スタッフが確認・修正して「登録する」と、期間のない内容は今と同じく「よくある質問」としてRAGに入り、期間のある内容は資料になる（6章）。「案内しない」も今と同じ
- 判定の理由を必ず出す。Nemotronの判定は誤ることがあるため、スタッフが見て不要なら「案内しない」で外せるようにする

## 6. 回答の登録先

スタッフが「登録する」を押したときに、確定した回答文を中型で判定して登録先を決める。スタッフが下書きを書き換えることがあるため、下書きを作った時点ではなく登録の時点で判定する。

| 回答の内容 | 例 | 登録先 |
|---|---|---|
| 日付で変わらない | 「コインランドリーは徒歩3分の○○にございます」 | 「よくある質問」としてRAG（`insertDocument`、今と同じ） |
| 期間・日付・季節で変わる | 「年末年始（12/29〜1/3）の大浴場は24時まで営業します」「冬季は屋外プールを休業します」 | 資料（文章）として登録（`info-sources.ts` の `createSource`）。AIが施設・項目・期間を読み取り、館内の情報の確認画面でスタッフが承認したものだけを回答に使う |

- 判定の結果（`kind`: `faq`／`source`）と理由は強制ツール呼び出しで受け取る。期間があるか迷うときは資料にする（承認を挟むほうが安全なため）
- 資料にしたときは、画面に「期間のある内容のため、館内の情報で確認してから案内に使います」と出し、確認画面へのリンクを置く。提案は「回答済み」にし、登録した資料のID（`knowledge_gaps.source_id`）を残す
- 資料のタイトルは「未回答の質問から: <質問>」とする。読み取った値の出どころとして、館内の情報の画面に表示される
- 資料は承認されるまで回答に使われない。承認されるまでの間は、同じ質問にAIは引き続き答えられない（安全側）

## 7. 未決・検討事項

- **実行間隔**: 1日1回で足りるか。件数が多いホテルでは1時間ごとにして、1回あたりの会話を減らす
- **判定のモデル**: 中型で始める。小型で足りるかは検証する（ガードレールの後チェックでは小型が見逃した）
- **まとめるしきい値**: 実データで調整する。まとめすぎると別の質問が1件になる
- **費用**: 会話ごとに中型を1回。デモ規模は小さいが、本番は会話数に比例する。評価しない会話の条件を増やして抑える
