# AIの設定と外部連携の設定の整理

2026-09-28 決定・実装。マイグレーションは `20261010000000_ai_settings.sql`。`000_plan.md` 4.7（指示・ガードレール・外部連携）と 4.8（権限）の画面の置き場所と、守らせ方を見直す。

## 0. 方針と決定事項

- **画面は「AIのどこに効くか」で分ける**。専門知識のないスタッフが、プロンプトとRAGといった仕組みの違いを意識しなくて済むようにする
  - 管理PCの「案内情報」を **「AIの設定」** にし、答える内容（案内情報）・答え方（指示）・連携の使い方（利用ルール）をまとめる。答える内容はゲストへの回答とスタッフのAI相談の両方に効き、答え方はゲストへの回答だけに効くため、左の一覧の見出しに効く範囲を添える（当初の名前「ゲスト対応AI」はAI相談にも効くことが伝わらないため変更。2026-09-29）
  - 外部連携は **「つなぐ」（`/manage`、開発者・経営）** と **「使い方」（`/admin`、現場）** に分ける
- **ガードレールの画面は廃止**。守らせ方の仕組みは内部に残す
  - 必ず人に引き継ぐ条件: 内部で常にON（安全・強い不満・スタッフと話したい・2回答えられない。判定は仕様に依存するため設定させない）
  - してはいけないこと: 指示・利用ルールを保存するときに上位モデル（Ultra）が「回答後に二重チェックすべきこと」を抜き出し、いまの後チェック（`checkReply`、Super）で守らせる。ホテルが何を書いても守る固定の項目も持つ
  - 確定前に必ずお客様へ確認: 廃止し、上の抜き出しの対象に含める
- **業務ごとの指示は1本にする**。区分ごとに見出しを付けずに並べていただけで、分ける効果が小さかった。クレーム向けの指示は「苦情・不満を言われたときは〜」と条件付きで書く
- **Webページの取得（Tavily）は設定を持たない**。資料（URL）の登録・取得頻度・反映のしかたは管理PCの資料で扱い、外部情報の使い方は内部の固定の指示にする。Tavilyのコストはサービス側の負担で利用者には見せない（`/manage` からも消す）。Best Use of Tavily の条件（実行時の呼び出し）は定期取得で満たしたまま
- **MCPのツールはAIが選んで使う**。呼ぶツールをコードで決め打ちしない。MCPで足りない連携は導入時の個別対応とし、ハッカソンではMCP連携だけを前提にする
- **ツールごとに選ぶ**。項目ごとの読み書き権限（予約内容・お客様メモ・料金…）は、ツールごとの許可に置き換える。AIに使わせるかは `integration_tools.ai_enabled`（外部連携の画面だけで設定）、人（スタッフのAI相談）はツールの権限 `integration.<slug>.<ツール名>`
- **ツールの種類（読み取り／書き込み）は持たない**（2026-09-29）。MCPは読み書きとも同じエンドポイントへの `tools/call` で、種類は相手の自己申告（`readOnlyHint`）しかないため。ツールごとに「AIに使わせるか」「スタッフの確認後に送るか」だけを選び、呼び出しはすべて監査ログに残す。MCP側でツールが適切に分かれていれば、ツールの単位で守れる（1つのツールが読み書きを兼ねる場合や、返す中身までは縛れない）
- **メンバーと権限の画面からAIエージェントを外す**（2026-09-29）。AIの権限（オーダー登録・引き継ぎの作成）はどこでも確認しておらず、連携のツールは外部連携で設定するため。プリセットのグループ「AIエージェント」は削除し、Webページの取得も権限を見ない
- **外部システムのメンバーは、実績の出力口の接続元にする**（2026-09-29、`20261013000000_export_clients.sql`）。当システムに接続してくる側（`/api/mcp/work-events`）で、出ていく側の連携先とは別物（旧デモの名前「予約・客室管理システム」と `integrations.member_id` の紐づけはやめた）。接続元ごとにトークンの環境変数名（`members.token_env`）を持ち、送られてきたトークンで接続元を特定して、その接続元の権限（`integration.work_events.read`、個別付与）を確認し、呼び出しを監査ログに残す。設定は `/manage/integrations` の「実績の出力口」で行い、メンバーと権限の画面はスタッフだけにする。プリセットのグループ「外部連携（読み取り）」は削除
- **書き込みの形式チェック（`【AI引継】` で始まるか）は廃止**。利用ルールは自由に書けるのに、コードが初期値の形式を決め打ちしていたため。誰が・いつ書いたかはシステムが引数で付け、利用ルールは本文の書き方だけを決める

## 1. 画面

### 管理PC `/admin`

```
AIの設定（旧 案内情報。URLは /admin/knowledge のまま）
├ 答える内容（ゲスト・AI相談の共通）
│  ├ 未回答の質問
│  └ 資料（URLの取得頻度・反映のしかた。Tavilyの名前は出さない）
├ 答え方（ゲストへの回答）
│  └ 指示（1本。保存すると「AIが回答後に重点チェックすること」を抜き出して表示）。旧「過去の会話で試す」は廃止（2026-09-29）
├ 連携の使い方
│  ├ 連携先の一覧
│  └ 連携先ごとの1ページ
│     ├ AIが使えること（ツールの一覧。/manage で許可したもの。MCPの description・読む／書く・用途・確認の要否。見るだけ）
│     ├ 利用ルール（1本。旧 読み取りルール＋書き込みルール）＋ 抜き出したチェック項目
│     └ 最近の書き込み（確認待ち・送れなかったものを上に）
└ 館内の情報（全体・各施設。ゲスト・AI相談の共通。一覧が長くなるため最後）
オーダー管理（変更なし）
対応アラート（変更なし）
```

- 「連携の使い方」の最初の画面は連携先の一覧（名前・つながっているか・AIが使えるツールの数・確認待ちの件数）
- 左の一覧は権限ごとに出し分ける（2章）

## 3. 処理

### 3.1 回答後のチェック項目の抜き出し

- 指示・利用ルールを保存したら、Ultra に「ゲストへの回答の後にチェックすべきこと（約束・提供・助言してはいけないこと、確定前に確認すべきこと）」を抜き出させ、`reply_checks`（出どころ＝指示／連携先、本文）を差し替える
- 固定の項目（値引き・補償の約束、他のお客様の情報、体調への助言、他社の紹介）はコードに持つ
- `checkReply` は固定の項目＋抜き出した項目で判定する（中型。いまと同じ）。違反なら止めて人へ引き継ぐ
- 抜き出しに失敗したら保存は通し、前回の項目を残して画面に「チェック項目を更新できませんでした」と出す

### 3.2 必ず人に引き継ぐ条件

- `guardrails` の `handoff_condition` と `enabledHandoffCodes` を廃止し、4つの条件を常に判定する

### 3.3 指示

- `ai_instructions` の `scope = 'pattern'` を廃止し、`common` だけにする。移行でクレームの指示を条件付きの文にして `common` に足す
- 回答係の指示は「## ホテルの指示」に1本を入れるだけ（業務による出し分けはなくなる）

### 3.4 連携係（MCPのツールをAIが選んで使う）

- 回答係にはツールを持たせない方針（12章: ツール呼び出しを文字で書く・同じ呼び出しを216回繰り返した）は維持する。ツールを使うのは別の **連携係** とし、結果を文章にして回答係に渡す
  - Super・thinkingオフ、ツール呼び出しは1回の発言で最大4回、同じ引数の呼び出しは打ち切る
  - 渡すのは、AIエージェントに許可されたツールと、その連携先の利用ルール
  - 呼ぶのはルーターが連携を必要とした発言だけ（案内・オーダーだけの発言では呼ばない）
- **引数の固定**: ツールの入力に `reservation_id`・`hotel_id` があれば、サーバーがゲスト本人の値で上書きする。AIは他人の予約を指定できない。スタッフのAI相談ではスタッフ本人の権限で絞る
- **書き込み**: 書くツールはその場で呼ばず `integration_writes` に積む。スタッフの確認が必要なツールは確認待ち、それ以外はすぐ送る。引き継ぎの書き戻し（旧 `writeBackHandoff`）も連携係が利用ルールに沿って書くツールを選ぶ
- **ゲスト文脈の取得はコードのまま**: 会話の最初の予約内容の取得は本人確認に当たるため、`/manage` で連携先に「ゲストの予約を取得するツール」を指定し、変換層（`pms.ts`）で呼ぶ。料金などはここで落とす。このツールは連携係には渡さない
- `pmsIntegration()`（MCPの連携は1つという決め打ち）をやめ、連携先を複数持てるようにする

### 3.5 Webページ（Tavily）

- `web_fetch` の連携は `integrations` に残し（取得の記録に使う）、画面から外す
- 外部情報の使い方（`externalReadRule`）は、いまの文を内部の固定の指示にする
- 項目ルール `external_updates` の確認は外し、権限 `integration.web_fetch.read` だけを見る

## 4. データの変更

- `reply_checks` を追加（`hotel_id`・`source_type`（instruction / integration）・`integration_id`・`body`・`sort`）
- `integration_tools` を追加（`integration_id`・`name`・`description`（MCPから取得した時点のもの）・`access`（read / write）・`ai_enabled`・`use_in`（guest / staff）・`require_staff_confirm`・`guest_context`（ゲストの予約を取得するツール））。旧 `integration_field_rules` は削除
- `ai_instructions`: `scope` を `common`・`integration`（利用ルール）にする。`integration_read` と `integration_write` は1本にまとめて移す
- `guardrails` を削除。`config_revisions.kind` から `guardrails` を外す
- `integration_writes.hold_reason` の「形式が合わない」の保留は使わなくなる（保留は送信の失敗だけ）

## 5. 実装の順番

1. **ガードレールと指示**: 引き継ぎ条件を常時ONに、`reply_checks` と抜き出し、指示を1本に、`guardrails` の削除
2. **画面の移動**: 管理PCの「AIの設定」（答える内容・答え方）、`/manage/policy` の削除、`/manage` の外部連携からWebページを外す
3. **連携の分割**: `integration_tools`、`/manage` の「つなぐ」（ツールの取得と許可）、管理PCの「連携の使い方」（ツール一覧・利用ルール・確認待ちの書き込み）、形式チェックの廃止
4. **連携係**: ゲスト対応での MCP ツールの自律利用、引き継ぎの書き戻しの置き換え
5. スタッフのAI相談（2026-09-29 実装）: 連携先のツールは、AIエージェントと相談しているスタッフの両方に権限があるときだけ使う（人・AI共通のツール1つ＝権限1つ）。ゲストの特定（予約の検索）はいまのコードの照合のまま、話題のゲストが1人なら連携係が読み取りのツールを選ぶ（書き込みはしない）。ゲストの情報を見られるグループ（`handling.consult.guest`）には予約・客室管理システムの読み取り4つを付けた（`20261011000000_staff_tool_permissions.sql`）。廃止した担当席のダミーアカウントも同じマイグレーションで削除した
6. （未着手）アクティビティ予約のモックMCP（連携先が複数あることを見せる）

各段階で `npm run typecheck`・`lint`・`build` と、`npm run try:guest` で回答・引き継ぎ・書き戻しを確かめる。

## 6. 実装で決めたこと・懸念

- 連携係は、ルーターが「周辺・外部の予約」「予約・客室」と判定した発言と、引き継ぎの書き戻しで動く。好みなどを書くのは、それらの発言の中で利用ルールに当たるときだけ（すべての発言では動かさない）
- 「試してみる」（旧 過去の会話で試す）は、判定が誤りやすく使われないため廃止した（2026-09-29）
- 旧 業務ごとの指示と確定前の確認は、マイグレーションで共通の指示に条件付きの文として足した

- 連携係が1段増えるので、連携の必要な発言は応答が約1〜2秒遅くなる
- 項目ごとの権限をやめるため、許可したツールが料金などを返せばAIに渡る。ツールの説明で読める内容を確かめて許可する運用にする（ゲスト文脈の取得は変換層で落とす）
- 抜き出しの品質は Ultra に依存する。画面に出して、スタッフが指示の書き方で直せるようにする
- `000_plan.md` の 4.3（パターン別の担当）はルーターの5パターンのまま残る（指示の区分とは別）
