# 未回答の質問と引き継ぎ（対応アラート）

2026-09-27 時点の実装。管理PC（`/admin`）のサイドバーの区分けを考える中で整理し、その後に引き継ぎ周りを作り直した内容をまとめる。

## 1. 管理PCのサイドバーの区分け（区分けの見出しは未実装）

サイドバーの項目は `src/app/admin/nav-items.ts` で定義している。ホームは削除し、`/admin` はサイドバーの一番上に移る。今は見出しなしで並べている。

| 区分 | 項目 | 画面 |
|---|---|---|
| A. AIの情報源 | 案内情報（旧 館内の情報と外部の情報源を統合。`docs/006_guide_info.md`） | `/admin/knowledge` |
| | （未回答の質問） | 案内情報の中（`/admin/knowledge/questions`） |
| B. オーダー関連 | オーダー | `/admin/orders` |
| | 品目・担当設定 | `/admin/items` |
| C. オーダー以外のゲスト応対 | 対応アラート | `/admin/handoffs` |

- 「未回答の質問」はAに置く。スタッフの回答は質問したゲストには届かず、知識（RAG）に入るため（2章）
- 「未回答の質問」は案内情報の左の一覧の先頭に置いた（2026-09-27）。左の一覧は権限ごとに出し分け、未回答の質問の権限だけの人には施設を出さない
- `/admin/documents` は案内情報の「全体」欄に統合し、今はリダイレクトだけが残っている。区分けには入れない
- 「引き継ぎ・クレーム履歴」は「対応アラート」に名前を変えた（7章）

## 2. 未回答の質問の動き

> 2026-09-27 に、会話ログを定期的に評価して見つける方式に置き換えた（`docs/004_knowledge_gap_review.md`）。以下は置き換える前の方式で、リアルタイムの記録（`recordUnanswered`）はもうない。

`src/server/questions.ts` の処理。

1. **記録**: AIが答えられなかった質問を、質問文だけ `unanswered_questions` に入れる。どのゲストの、どの会話の質問かは保存しない。同じ文面の質問は1件にまとめ、`ask_count` を増やす
2. **一覧**: 管理PCで、聞かれた回数の多い順に並べる
3. **回答**: 「よくある質問: …」という文書としてRAGに登録する。以降は同じ質問にAIが答えられる
4. **案内しない**: 知識には入れず、一覧から外すだけ

この機能は、目の前のゲストに人が代わりに答えるためのものではない。AIが答えられなかった穴を埋め、次から答えられるようにするためのもの。

未回答の質問に入れるかどうかは、回答係（中型Super）が `answer` ツールで返す `unanswered_questions` で決まる。一覧が空でも、回答文に「スタッフに確認」「確認してご連絡／お知らせ」があれば、ゲストの発言全体を記録する（LLMが一覧を空で返すことがあるため、正規表現で補っている）。

## 3. 想定している使い方

- 答えられずに困っているゲストには、リアルタイムに**対応アラート**（C）で人が応対する
- 同じ質問が溜まってきたら、**未回答の質問**（A）で回答し、AIが答えられるようにする。件数で自動的にAIへ回す仕組みはなく、回答するかどうかはスタッフが判断する
- 定期評価に置き換えた後は、AIが答える前にスタッフへ切り替わった質問や、スタッフが代わりに答えた質問も未回答の質問に入り、スタッフの返信が回答の下書きになる（`docs/004_knowledge_gap_review.md`）

## 4. 引き継ぎの種類と対応アラートの分類

引き継ぎ（`handoffs`）の種類はきっかけごとに保存し、管理PCの画面ではそれを4つの分類にまとめる。分類は `src/lib/handoff-kinds.ts` で定義している。種類を細かく保存しておくので、分類を変えたくなってもデータを移し替えずに済む。

| きっかけ | 判定するもの | 種類（`kind`） | 対応アラートの分類 | ゲストの取り消し |
|---|---|---|---|---|
| 急病・けが・火事など | ルーター（小型）の `safety` | `safety` | 安全 | 不可 |
| 画面の「スタッフと話す」ボタン | ゲストが押す（LLMなし） | `talk_request` | スタッフとの会話希望 | 引き受け前なら可 |
| 「スタッフと話したい」の発言 | ルーターの `wants_staff` | `talk_request` | スタッフとの会話希望 | 引き受け前なら可 |
| クレーム・強い不満 | ルーターの `complaint` 分類、または `strong_emotion` | `complaint` | クレーム・強い不満 | 不可 |
| 業務の担当が「人」に設定されている | 設定（業務の分類はルーター） | `staff_assigned` | AIでは対応できない | 不可 |
| 回答が禁止事項に反した | 後チェック（中型）の判定 | `guardrail_blocked` | AIでは対応できない | 不可 |
| 同じ会話で2回答えられなかった | 回数はDBで数える。「答えられなかった」は回答係の判断 | `unanswerable` | AIでは対応できない | 不可 |
| 回答の生成・禁止事項のチェックが失敗した | 例外・出力の検証（機械） | `system_error` | AIでは対応できない | 不可 |
| オーダーが期限を過ぎた | 機械（cron、`escalation.ts`） | `overdue_order` | 出さない（オーダーボードだけ） | 不可 |

- 「必ず人に引き継ぐ」条件のオン・オフや「2回で引き継ぐ」といった枠は、ガードレールの設定（`guardrails.code`: `wants_staff` / `strong_complaint` / `unanswered_twice` / `safety`）としてデータで固定している
- その条件に当てはまるかどうかの判定は、ルーターと回答係のLLMが行う。ルーターが安全やクレームを見逃すと、引き継ぎは作られない
- ゲストが取り消せるのは、ゲスト自身が求めた引き継ぎ（`guest_requested = true`）だけ。安全やクレームは、ガードレールで必ず人に回すと決めたものなので取り消せない

### 1通の処理の順番

`src/server/guest-chat.ts` の `handleGuestMessage`。

1. ルーターで要望に分解する
2. 安全に関わる内容なら、ここで人に引き継いで終わる
3. オーダーを発行する（チケット）
4. クレーム・強い不満の引き継ぎを作る
5. 「スタッフと話したい」なら、ここで人に引き継いで終わる。同じ発言のオーダーとクレームは処理済み。オーダーがあれば「ご依頼を承りました。あわせてスタッフにおつなぎします。」と返す
6. 業務の担当が「人」なら、人に引き継いで終わる
7. 回答係が回答を作る。作れなければシステムの不具合として引き継ぐ
8. 回答を禁止事項でチェックする。違反なら回答を出さずに引き継ぐ。チェック自体が失敗したらシステムの不具合として引き継ぐ
9. 同じ会話で2回答えられなかったら引き継ぐ（7でシステムの不具合になったときは重ねない）

どの引き継ぎにも、きっかけになったゲストの発言（`message_id`）を記録する。ボタンからの依頼は発言がないので記録しない。

ルーターは「スタッフと話したい」そのものをクレームの要望にすることがある。指示で禁止したうえで、`wants_staff` のときは会話希望だけを書いた短い要約（15文字以内）を要望から外している（`router.ts` の `isTalkRequestOnly`）。「騒音のためスタッフと話したい」のように苦情を含む長めの要約は残す。

## 5. ゲスト画面の「スタッフと話す」

`src/app/guest/[reservationId]/guest-chat.tsx` と `src/server/guest-chat.ts`（`requestStaff`・`cancelStaffRequest`）。

| 状態 | ヘッダーのボタン | ヘッダー下の帯 |
|---|---|---|
| 依頼なし | 「スタッフと話す」（押した直後は「おつなぎしています…」） | なし |
| 連絡済み・スタッフが引き受ける前 | 「スタッフに連絡済み」（押せない） | 「スタッフにおつなぎしています。」と「取り消す」 |
| スタッフが引き受けた後 | 「スタッフが対応中」（押せない） | 「スタッフが対応しています。」 |

- 取り消すと、状態が `cancelled` になり、チャットに「スタッフへのご連絡を取り消しました。」と出る。スタッフへの通知は既読にし、現場スマホの一覧から消える
- 引き受けた後は取り消せない（「すでに対応を始めているため、取り消せませんでした」）
- 1つの会話で対応中のゲストの依頼は1件まで。DBの部分一意索引 `handoffs_active_guest_request` で保証し、連打・複数タブ・ボタンを押した後の「スタッフと話したい」でも2件目は作らない（「すでにスタッフにおつなぎしています」と返す）
- スタッフと話している間（ゲストの依頼が未対応・対応中）は、ゲストの発言にAIは回答せず、会話に記録するだけ（ルーター・安全の判定・オーダーの発行も行わない）。スタッフは現場スマホの引き継ぎ詳細か、管理PCの会話パネルから返信する。対応完了やゲストの取り消しでAIの応対に戻る。ゲスト画面の帯には「メッセージはスタッフに届きます」と出し、入力欄は「スタッフへのメッセージ」にする
- ボタンと発言は同じ関数 `handOffToStaff` で引き継ぐ。違いは、発言のほうはルーターの判定とガードレールの `wants_staff` がオンであることが前提で、ゲストの発言が会話に残ること

## 6. システムの不具合

回答の生成（`generateAnswer`）や禁止事項のチェック（`checkReply`）が失敗したときは、種類 `system_error` で引き継ぐ。ゲストには「確認してすぐにご連絡いたします」などと返しているので、スタッフの応対は他の引き継ぎと同じく必要。

- 原因は `src/lib/llm/errors.ts` の `classifyLlmError` で分ける。Mastra が包んだエラーや AI SDK の再試行（`RetryError`）をたどって元のエラーで判定する

| 原因（`failure_cause`） | 表示 | 例 |
|---|---|---|
| `timeout` | 応答がタイムアウト | `TimeoutError` |
| `api_error` | APIエラー | HTTP 429・500 など（`APICallError`） |
| `invalid_output` | 回答の形式が不正 | 再試行しても `answer` ツールで回答が返らない（`InvalidOutputError`）、回答文が空 |
| `unknown` | 原因不明 | 上記以外 |

- 引き継ぎに、失敗した処理（`failure_stage`: `answer`＝回答の生成 / `guardrail`＝禁止事項のチェック）、原因、生のエラー（`failure_detail`）、モデル名（`model_id`）を残す。禁止事項のチェックが失敗したときは、止めた回答も `failure_detail` に入れる
- 禁止事項で回答を止めたとき（`guardrail_blocked`）も、`failure_detail` に理由と止めた回答を入れる
- 対応アラートでは、原因と「直近24時間で同じ原因 ○件」を出す。単発の失敗か、障害が続いているかの見分けに使う
- 現場スマホには原因を出さない（ゲストへの応対に必要ないため）

## 7. 対応アラート（`/admin/handoffs`）

`src/app/admin/handoffs/page.tsx`（一覧）と `conversation-panel.tsx`（右の会話パネル）。

- **一覧**: 分類（安全／スタッフとの会話希望／クレーム・強い不満／AIでは対応できない）と状態（未対応／対応中／対応完了／ゲストが取り消し）で絞り込む。「AIでは対応できない」を選ぶと、理由（担当が人／禁止事項に反した／2回答えられなかった／システムの不具合）でさらに絞り込める。行には理由のラベルと、システムの不具合なら原因を出す
- **会話パネル**: 行を選ぶと右側に開く（URLの `?id=`）。そのゲストとの会話をすべて出し、引き継いだ時点のメッセージ（`message_id`、なければ引き継いだ時点の最後のメッセージ）に枠を付けて、パネルの中だけをそこまでスクロールする
- **応対**: パネルの上部で「引き受ける」「対応完了にする」。下の入力欄からゲストに返信でき、引き受け前に返信すると返信した人が引き受けたことになる（`replyHandoffAdminAction`）。返信や新しい発言が届くと一番下までスクロールする。対応中のあいだは15秒ごとに更新する
- オーダー遅延は、対応アラートには出さない。オーダーボードの期限超過の表示と、上長への通知で気づける
- 権限は、一覧の表示が `handling.complaint.view`、引き受け・返信・完了が `handling.handoff.accept`

## 10. 残っている課題

- **1回目で答えられなかったときの引き継ぎがない**: AIはゲストに「スタッフに確認してご連絡します」と伝えるが、1回目では引き継ぎを作らず、誰にも通知されない。未回答の一覧にはどのゲストの質問かが残らないため、スタッフが後から連絡することもできない。回答係が未回答と判定したら1回目から `unanswerable` の引き継ぎを作り、ガードレールに「1回で人へ」のような条件を追加してオン・オフできるようにする案がある

未回答の質問に入らない場面が多いことは、定期評価への置き換え（`docs/004_knowledge_gap_review.md`）で解消する予定。

| 場面 | 未回答の質問に入るか | 引き継ぎができるか |
|---|---|---|
| 回答文そのものを作れなかった | 入らないことがある | できる（システムの不具合） |
| 回答はできたが、一部に「スタッフに確認します」と答えた | 入る | できない |
| 同じ会話で2回目の「答えられない」 | 入る | できる（`unanswered_twice` が有効な場合） |

- **取り消しても残るもの**: お客様メモへの書き戻しは応答の直後に走るため、ふつうは取り消す前に「スタッフとの会話を希望」と書かれる（書き戻しの時点で取り消し済みなら書かない）。実績（`work_events`）にも引き継ぎとして1件残る
- **スタッフがゲストの新しい発言に気づきにくい**: スタッフと話している間のゲストの発言は通知されない。管理PCの会話パネルは15秒ごとに更新するが、現場スマホの引き継ぎ詳細は開き直すまで新しい発言が見えない
- **現場スマホは分類に合わせていない**: 表示名だけ共通の定義を使っている。オーダー遅延も現場スマホの引き継ぎ一覧には出る
- **サイドバーの区分けの見出し**（1章）は未実装
- 余裕があれば、対応アラートの会話パネルから「この回答を知識に登録する」を選べるようにし、未回答の質問とのつながりを画面上でも分かるようにする
