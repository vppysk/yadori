# 未回答の質問と引き継ぎの整理

2026-09-27 時点の実装を調べた結果。管理PC（`/admin`）のサイドバーの区分けを考える中で整理した。

## 1. 管理PCのサイドバーの区分け（案）

サイドバーの項目は `src/app/admin/layout.tsx` で定義している。「ホーム」は区分に入れず、先頭に置く。

| 区分 | 項目 | 画面 |
|---|---|---|
| A. AIの情報源 | 館内の情報 | `/admin/knowledge` |
| | 外部の情報源 | `/admin/sources` |
| | 未回答の質問 | `/admin#questions`（ホームの一区画） |
| B. オーダー関連 | オーダー | `/admin/orders` |
| | 品目・担当設定 | `/admin/items` |
| C. オーダー以外のゲスト応対 | 引き継ぎ・クレーム履歴 | `/admin/handoffs` |

- 「未回答の質問」はAに置く。スタッフの回答は質問したゲストには届かず、知識（RAG）に入るため（2章）
- 「未回答の質問」だけは独立した画面がなく、ホームの一区画になっている。区分の見出しを付けて並べると、この項目だけホームに飛ぶ。必要なら `/admin/questions` として独立させる
- `/admin/documents` は「館内の情報」の「全体」欄に統合し、今はリダイレクトだけが残っている。区分けには入れない

## 2. 未回答の質問の実際の動き

`src/server/questions.ts` の処理。

1. **記録**: AIが答えられなかった質問を、質問文だけ `unanswered_questions` に入れる。どのゲストの、どの会話の質問かは保存しない。同じ文面の質問は1件にまとめ、`ask_count` を増やす
2. **一覧**: 管理PCで、聞かれた回数の多い順に並べる
3. **回答**: 「よくある質問: …」という文書としてRAGに登録する。以降は同じ質問にAIが答えられる
4. **案内しない**: 知識には入れず、一覧から外すだけ

この機能は、目の前のゲストに人が代わりに答えるためのものではない。AIが答えられなかった穴を埋め、次から答えられるようにするためのもの。

## 3. 想定している使い方

- 答えられずに困っているゲストには、リアルタイムに**引き継ぎ**（C）で人が対応する
- 同じ質問が溜まってきたら、**未回答の質問**（A）で回答し、AIが答えられるようにする。件数で自動的にAIへ回す仕組みはなく、回答するかどうかはスタッフが判断する

## 4. 判定の仕組み

発言の読み取りや「答えられたか」の判定はLLMが行う。その判定をもとに引き継ぎを作るかどうかは、コードのルールで決まる。

### 未回答の質問に入れるかどうか

`src/server/guest-chat.ts` の `handleGuestMessage` での処理。

- 回答係（中型Super）が `answer` ツールで返す `unanswered_questions` に入れた質問を、そのまま記録する
- 一覧が空でも、回答文に「スタッフに確認」「確認してご連絡／お知らせ」があれば、ゲストの発言全体を記録する。LLMが一覧を空で返すことがあるため、正規表現で補っている。LLMが別の言い回しをした場合は記録されない

### 引き継ぎを作るかどうか

| きっかけ | 判定するもの | 場所 |
|---|---|---|
| 安全（急病・けが・火事など） | ルーター（小型）の `safety` | `guest-chat.ts` `handleGuestMessage` |
| 「スタッフと話したい」 | ルーターの `wants_staff` | 同上 |
| 画面の「スタッフと話す」ボタン | ゲストがボタンを押す（LLMなし） | `guest-chat.ts` `requestStaff` |
| クレーム・強い不満 | ルーターの `complaint` 分類、または `strong_emotion` | `guest-chat.ts` `handleGuestMessage` |
| 業務の担当が「人」に設定されている | 設定で決まる（業務の分類はルーター） | 同上 |
| 回答文が空だった | 機械の判定（LLMの失敗） | 同上 |
| 禁止事項に反した | 後チェック（中型）の判定 | `guardrails.ts` `checkReply` |
| 同じ会話で2回答えられなかった | 回数はDBで数える。「答えられなかった」は回答係の判断 | `guardrails.ts` `unansweredCount` |
| オーダーが期限を過ぎた | 機械（cron） | `escalation.ts` |

- 「必ず人に引き継ぐ」条件のオン・オフや「2回で引き継ぐ」といった枠は、ガードレールの設定（`guardrails.code`: `wants_staff` / `strong_complaint` / `unanswered_twice` / `safety`）としてデータで固定している
- その条件に当てはまるかどうかの判定は、ルーターと回答係のLLMが行う。ルーターが安全やクレームを見逃すと、引き継ぎは作られない

## 5. AIが答えられなかったときの動きと、現状の抜け

| 場面 | 未回答の質問に入るか | 引き継ぎができるか（スタッフに通知） |
|---|---|---|
| 回答文そのものを作れなかった | 入らないことがある | 毎回できる |
| 回答はできたが、一部に「スタッフに確認します」と答えた | 入る | できない |
| 同じ会話で2回目の「答えられない」 | 入る | できる（`unanswered_twice` が有効な場合） |

**抜け**: 1回だけ答えられなかった場合、AIはゲストに「スタッフに確認してご連絡します」と伝えるが、引き継ぎは作られず、誰にも通知されない。未回答の一覧にはどのゲストの質問かが残らないため、スタッフが後から連絡することもできない。3章の使い方のうち、リアルタイムの対応がこの場面では成り立たない。

## 6. 修正案（未着手）

- 回答係が未回答と判定したら、1回目から `unanswerable` の引き継ぎを作ってスタッフに通知する。ガードレールに「1回で人へ」のような条件を追加し、オン・オフできるようにする
- 未回答の質問は今のまま、同じ質問が何回聞かれたかを数える一覧として使う
- 余裕があれば、引き継ぎの対応画面から「この回答を知識に登録する」を選べるようにし、2つの機能のつながりを画面上でも分かるようにする
